Open decisions — needed now

Decision 01 · blocks Tanishq

Is clip A a Hindi clip, or English with a Hindi override?

Auto-language routing means an English clip now produces English narration. The boardroom clip is English, but the demo script says "approve the Hindi line" and closes on Indian languages. Either pick a Hindi hero clip, or demo English→English first and flip the override to Hindi as the second beat. This decides which clip gets trimmed first.

Decision 02 · verify before promising

Does Bulbul v3 support en-IN, and with which speaker?

TTS covers fewer languages than text generation. If English speech isn't supported, an English clip in auto mode pauses for language selection in the middle of the demo. Twenty-minute check, not a 3 PM discovery.

Decision 03 · demo shape

Live upload, or cached run on stage?

A clip takes roughly two minutes to process and the live segment is two minutes long. A fresh upload eats the entire window. Run the demo on a warm cache so it returns in seconds, say so plainly, and keep a genuine fresh run ready if a judge asks.

Decision 04 · unblocks three people

Who writes the fixtures?

One person hand-writing English and Hindi fixture jobs by 10:15 is a bottleneck three people wait on. Better: Aryan freezes the field names and the job-dir skeleton, then each owner writes their own output fixture. Still one author per file, so merge safety is unchanged.

Four verticals — nobody edits anyone else's files

Merging killed us last time. Git conflicts need two people in one file, so no two people are ever in one file. The verticals talk to each other only through JSON in jobs/<id>/.

The five rules that keep it merge-free

  1. One owner per path. Need a change in someone's file? Message them. Never edit it yourself.
  2. Contracts are frozen fixtures, committed first. Once committed, those shapes are the interface. Shape changes go through Aryan and get announced out loud.
  3. Every module runs standalone. python -m drishti.gaps jobs/test1/ reads the job dir, writes its own JSON, prints a summary. You test your vertical without anyone else's code.
  4. Integration by substitution. The pipeline runs end-to-end from 11:00 with every stage faked. Real modules swap in one at a time — a late module never blocks the gate.
  5. Trunk-based, tiny commits. Straight to main every 20–30 minutes, git pull --rebase before every push. Disjoint files make every rebase automatic.

common.py is frozen once the sprint starts — but make it additive-only: new functions may be appended, existing ones never modified or renamed. That keeps merges trivial while leaving an escape valve at 11:30.

The contract — the only shared surface

Job directory

jobs/<id>/ input.mp4 status.json Aryan gaps.json Nishant chunks.json Nishant transcript.txt Nishant language.json Nishant scenes.json Ritika narration.json Tanishq narration_XX.wav Tanishq output.mp4 Nishant

Modules never write status.json — only the pipeline does. New job dir per upload, always: a stale chunk cache on a different clip poisons everything downstream.

Stages and endpoints

validate→ gaps→ scenes→ transcript→ narrate→ tts_fit→ mix→ done
  • POST /jobs — video + {language:"auto"} → {job_id}
  • GET /jobs/{id} — status, detected and output language, artifact links
  • POST /jobs/{id}/narration/{n} — approve or edit a line
  • GET /jobs/{id}/artifacts/…

Two places the pipeline stops for a human — language selection and narration approval. Build one generic awaiting state and one resume endpoint, not two bespoke flows. In Saaras chunk mode the transcript already comes out of gap detection, so transcript must not fire a second STT call.

Source-language routing — the M1 invariant

DRISHTI describes a video in the language spoken in it, unless someone explicitly asks for translation. English video, English narration. Hindi video, Devanagari Hindi narration. The pipeline never silently defaults to Hindi.

WhoDoes whatNever does
Nishant Keeps Saaras's language_code and probability per spoken chunk, picks the duration-weighted dominant language, writes language.json. Guess. Under two speech chunks, confidence below 0.70, or no dominant language → write unknown.

Increments — each one leaves us demo-ready

Increment 1 · Web product 12:30 → 13:45

CLI becomes "upload in a browser, watch it think, play the result." The evidence timeline is the centrepiece: dialogue in red, narration-safe windows in green, scene beats beneath. The narration card also shows withheld details — what the system refused to narrate.

Check: live browser upload of clip A, end to end. Screen-record it — fallback #2.

Increment 2 · Human approval 13:45 → 14:30

The pipeline pauses at narration; the line appears in the UI; edit or approve, then TTS continues. Broadcasters really do approve AD scripts before recording. It's also a hallucination safety net — and stage insurance, because we never play a line we haven't read.

Increment 3 · Memory and language 14:30 → 15:15

Entity memory carries characters across clips, so part two says "the same man in the grey suit" instead of describing him from scratch. Build that consistency version first; binding a spoken name to a face is the harder second step. Explicit Hindi ⇄ Tamil override lands here too.

Check: full product. Record the polished fallback and test the volume now, not at 4 PM.

Increment 4 · Smart context pauses 15:15 → 16:00

When no gap is long enough for essential context, the video freezes, Bulbul explains, and it resumes — real practice, called extended audio description. Capped at two pauses. Same renderer gives a scene-setting intro at t=0 almost free.

New file pauses.py — never edit a working mixer at 3 PM.

Rejected, do not reopen: voice cloning · WhatsApp or Twilio delivery · realtime description · long videos. After 1 PM the answer to new scope is the cut list.

The three minutes that decide it

0:00–0:30The problem, plainly. 34 million blind and low-vision Indians. Almost no Indian-language content carries audio description. Play five seconds with the screen hidden: this is what a film is for a blind viewer.
0:30–1:00How it's done today. A scriptwriter, a voice artist, a sound engineer. Days of turnaround, lakhs per hour of content — so in Hindi and Tamil it simply doesn't get made.
1:00–3:00Live. Upload → the evidence timeline fills in ("the music never stops; energy detection can't find these windows — Saaras can") → approve the line on screen → play it. Then one line each: the language flip, part two remembering the character, one context pause. Close on the outcome, not the stack.

Presenter: Tanishq. Laptop: Aryan. Rehearsed twice, timed. The fallback recording stays one keypress away — if the network stalls, narrate over it without apologising.

Aryan's backlog — for the gaps between integrations

  1. Content-hashed response cache in common.py, before the freeze. Makes reruns free, and makes the on-stage demo return in seconds.
  2. Transparency panel — per-stage latency and API call counts. When a judge asks whether this really works, we show receipts. Also produces the real number behind "about two minutes."
  3. Accessible UI pass — keyboard-navigable player, aria labels, visible focus. An accessibility product whose own interface is usable by a screen reader.
  4. Radio mode — one-click MP3 of the described mix. Blind users often just listen.
  5. QR hand-off — judges play the result on their own phone. Only if everything else is green; never promise it.
